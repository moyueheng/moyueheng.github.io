我一开始用 AI 编程，关注的是它能不能写函数、修 bug、补测试。后来发现，这只是第一层。

真正的变化不是「AI 帮我写代码」，而是软件工程的重心在迁移：

```text
过去：工程师主要负责写代码
现在：工程师越来越负责定义目标、组织上下文、设计验证、管理技术债
```

AI 降低的是编码成本，提高的是工程判断的价值。

## Vibe coding 的真正问题

Vibe coding 最大的问题不是代码能不能生成，而是生成之后这笔债值不值得背。

AI 可以在几个小时内写出一堆代码，但每一行代码都会变成未来要维护、要测试、要解释的技术债。所以更重要的判断变成了：

- 这个需求是不是值得做？
- 这个方案是不是值得背债？
- 这个任务应该拆到多小？
- 哪些上下文必须给 AI？
- 怎么证明 AI 做对了？

以后厉害的工程师，不是比 AI 更会写 CRUD，而是更会判断什么该写、什么不该写，以及怎么验证。

## 核心不是 prompt，而是环境

prompt 有用，但它是一次性的。真正能复利的是环境。

一个 AI 编程环境至少有三层：

```text
入口层：AGENTS.md / CLAUDE.md
能力层：Skills
验证层：Tests / CLI / CI / Review / MCP
```

- **入口层**解决「agent 进入项目后先知道什么」。
- **能力层**解决「遇到一类任务时按什么流程做」。
- **验证层**解决「它到底做对了没有」。

这也是我维护 `coding-everything` 的基本思路：不是收集一堆提示词，而是把成功的协作方式沉淀成一套可复用的工作系统。

> Prompt 是一次对话的技巧，环境是持续交付的基础设施。

## AGENTS.md 是启动协议

我不把 `AGENTS.md` 当 README。README 是写给人看的，告诉人这个项目是什么；`AGENTS.md` 是写给 agent 的，告诉它进入这个空间后应该怎么行动。

它回答的是这些问题：

```text
你现在在哪里？
这里最重要的规则是什么？
哪些目录代表什么含义？
改东西前先看哪里？
不能做什么？
做完之后如何验证？
遇到某类任务应该调用什么 skill？
```

这类文件的价值在于稳定入口。模型会变，工具会变，但只要 agent 每次进入项目都会读这些规则，我就能把项目习惯固化下来。

> `AGENTS.md` 不是说明书，而是 agent 的操作系统启动项。

## 分层的关键是继承

我倾向于把 `AGENTS.md` 分层放。子目录里的规则不是孤立生效，而是继承上一层目录的规则。

```text
上层 AGENTS.md：全局身份、硬规则、通用工作方式
  ↓
项目 AGENTS.md：项目结构、常用命令、主要 skill
  ↓
子目录 AGENTS.md：模块边界、局部约定、局部验证方式
  ↓
具体文档、代码、测试
```

这样可以把规则拆成层级，而不是在每个目录重复一遍。上层保持稳定，下层只写这个模块真正特殊的地方。

## 验证是最后一道边界

如果 Agent 写完代码后没有验证，那它只是生成了一段「看起来对」的文本。

我现在更愿意先定义验收方式，再让 Agent 开始改：

- 有没有一个能复现问题的测试？
- 改完之后哪个命令必须通过？
- 哪些行为需要人工检查？
- 失败时应该回滚还是继续迭代？

环境搭好之后，Agent 的能力才有边界；有了边界，才谈得上稳定交付。
